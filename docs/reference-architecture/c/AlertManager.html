Design guidance

  • SHOULD alert on hourly cost at early-warning and escalation thresholds.
  • SHOULD alert when agent error rates exceed thresholds, latency breaches SLOs, or systematic error patterns emerge.
  • MAY alert when agents reference information older than the session start time.
  • SHOULD tier reasoning-quality alerts (critical, warning, info) and tune thresholds to balance sensitivity against alert fatigue.
  • SHOULD alert when cost per interaction exceeds budget, token consumption spikes, or API call patterns suggest bugs or abuse.
  • SHOULD alert when hallucination rates exceed expected statistical variation, triggering investigation before user impact.
  • SHOULD alert on service-level indicators (e.g., service error rate) rather than pod-level events to avoid alert fatigue.
  • SHOULD alert on high GPU utilization, memory pressure, thermal throttling and GPU error-rate escalation.
  • SHOULD alert teams when validation failure rates spike above baseline thresholds.
  • SHOULD alert only on actionable SLO breaches with clear remediation, routed through on-call rotations.
  • SHOULD route by severity: warning to business-hours investigation, critical to immediate on-call notification.
  • SHOULD alert on percentile latency degradation (e.g., P95) and trigger incident response.
  • SHOULD route safety-violation alerts to security/ML teams and infrastructure alerts to operations teams.
  • SHOULD alert when organization-level cost exceeds the budget forecast so feature- and request-level investigation begins.
  • SHOULD tune thresholds and sensitivity to avoid alert fatigue from false positives (Ref8.09).
  • SHOULD route alerts by severity: critical pages on-call, high creates a ticket, medium schedules a review, low goes to the backlog.
  • SHOULD route privacy and security alerts to legal and security responders and regulatory alerts to the compliance officer.
  • SHOULD tier alerts by severity: critical alerts notify immediately, warnings update dashboards, informational alerts are only logged.
  • SHOULD measure and optimize alert precision (share of alerts requiring action) rather than alert volume.

Quantitative guidance

As stated by the sources; verify before use.

  • Cost alerts at 50% of hourly budget (warning) and 75% (escalate to on-call) (Ch1.8).
  • Alert examples: tool selection accuracy falling 94%->87% over three days; parameter validation failures rising 4%->12% (Ch3.8).
  • Critical: reasoning quality drop >15% from baseline within 24 hours; Warning: gradual degradation >5% per week over 3 weeks; Info: individual high-stakes traces scoring <60% (Ch3.9).
  • Meaningful alert example: service error rate rising from 0.1% to 5% (Ch4.2).
  • GPU normal operating range 30-80 C; thermal throttling at 85 C (Ref4.05).
  • Automated alert fired on P95 degradation from 1.2 s to 4.5 s (+275%) (Ch8.1).
  • A 15% rise in resolution time above baseline during a holiday surge triggered automated scaling (Ch10.1).
  • Humans receiving more than 100 alerts daily stop distinguishing critical from trivial (Ch10.4).
