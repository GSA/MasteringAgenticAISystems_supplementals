Retry Handler

Software componentTools & IntegrationOrchestration & Toolsarc:RetryHandler

A resilience component that automatically re-attempts transiently failed tool or API calls using exponential backoff and reports attempt progress.

Responsibility. Retries transient failures with backoff.

Design guidance

  • MUST retry transient failures with exponential backoff rather than treating them as task failure.
  • SHOULD show retry progress to users and let them cancel or skip the step.
  • MUST combine exponential backoff, jitter and a maximum retry count.
  • SHOULD retry only transient failures, distinguished by specific error codes.
  • MUST use idempotency keys or unique identifiers for write operations so retried requests do not execute twice.
  • SHOULD retry only the failed operation, reusing successful results preserved in state.
  • MUST retry only transient failures (network instability, TLS handshake failures, cold starts, brief rate limits, token-quota resets) and MUST NOT retry authentication failures, invalid requests, 404s or slowly-resetting quota exhaustion.
  • SHOULD add jitter to backoff delays so synchronized clients do not overwhelm a recovering service.
  • SHOULD cap attempts (typically 3-5) and maximum delay to avoid infinite retry loops and user-frustrating waits.
  • SHOULD hand over to fallback strategies when failures persist beyond the retry budget, since retries cannot distinguish persistent outages.
  • SHOULD back off exponentially (e.g., 1s, 2s, 4s) so retry load from many clients is spread over time.
  • MUST NOT retry permanent errors such as non-existent tools, authentication failures or parameter validation errors.
  • MUST implement retries with exponential backoff for transient network failures between microservices.
  • MUST use exponential backoff with jitter and a bounded retry budget rather than immediate unbounded retries.
  • SHOULD apply retries with exponential backoff to execution-tier failures only; retries do not fix planning or verification failures.
  • SHOULD queue and retry with exponential backoff on provider rate-limit (HTTP 429) responses.

Quantitative guidance

As stated by the sources; verify before use.

  • Example UI 'Attempt 2 of 3' during automatic retry (Ch1.1A).
  • Backoff doubles from 1 s to 2, 4, 8 s; production implementations typically cap at 3-5 attempts and 60 s maximum delay (Ch2.8).
  • Retry suits rate limits shorter than ~60 s; a 60,000 tokens-per-minute limit hit after 30 of 100 contracts was recovered with zero manual intervention (Ch2.8).
  • Example LLM retry delays 100 ms, 200 ms, 400 ms; general backoff 1 s, 2 s, 4 s up to a maximum (Ch6.5).
  • Backoff example 1 s, 2 s, 4 s for API calls; 100 ms, 200 ms, 400 ms for state-write retries (Ch8.2A).
