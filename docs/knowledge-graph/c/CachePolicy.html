Cache Policy

Data artifactModel ServingModelsarc:CachePolicy

A configuration specifying cache TTLs per layer, eviction policy, key normalization and coordination strategy.

Responsibility. Defines expiry, eviction and population rules for cache layers.

Design guidance

  • SHOULD set TTLs according to data change frequency; too long risks staleness, too short reduces hit rate.
  • SHOULD prioritize retaining frequently accessed, expensive-to-compute entries.
  • SHOULD select TTLs per data type balancing freshness against hit rate (e.g., minutes for pricing, real-time for balances).
  • SHOULD consult cache tiers in order (reasoning-chain templates, then embeddings, then tool results) and populate all tiers on a full miss.
  • SHOULD combine TTL to bound staleness, event-based invalidation after updates, and LRU eviction to prevent memory exhaustion.

Quantitative guidance

As stated by the sources; verify before use.

  • FAQ example TTL 3600 s (Ch1.8).
  • 5-minute TTL acceptable for product pricing but inadequate for account balances (Ch3.4).
  • Tool-result TTL example 5 minutes combined with event invalidation (Ch4.7).
  • RAG worked example: average latency 500 ms to 446 ms (11%), 30% for frequent questions; total cache memory ~340 MB (Ch4.7).
