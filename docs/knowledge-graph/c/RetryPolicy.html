Retry Policy

Data artifactTools & IntegrationOrchestration & Toolsarc:RetryPolicy

A configuration artifact stating which error classes are retryable, the maximum attempts or per-node retry budget, base and maximum backoff delays, and jitter.

Responsibility. Specifies when and how often failed calls may be retried.

Also known as: Retry configuration, Retry budget, max_retries

Design guidance

  • MUST distinguish retryable from non-retryable error classes.
  • SHOULD bound retries per workflow node when retry loops are expressed in a state graph.
  • SHOULD cap retries (e.g., two attempts) before escalation and vary the approach rather than repeating identical failed calls.
  • SHOULD classify network timeouts, temporary unavailability and rate-limit-exceeded as retryable, and invalid tool names, missing credentials and malformed parameters as non-retryable.

Quantitative guidance

As stated by the sources; verify before use.

  • 3-5 attempts; 60 s maximum delay (Ch2.8).
  • Batch ingestion retries up to 3 times with exponential backoff (Ch6.2B).
  • Exponential backoff example: wait 1 s, 2 s, 4 s ... up to a maximum delay (Ch6.3B).
