Circuit Breaker

Software componentTools & IntegrationOrchestration & Toolsarc:CircuitBreaker

A resilience component that stops calls to a persistently failing external dependency to prevent cascading failure and enable graceful degradation.

Responsibility. Stops calls to failing dependencies.

Also known as: Bulkhead, Per-agent circuit breaker

Design guidance

  • SHOULD be applied to persistent failures, complementing retries for transient ones.
  • MUST be placed between agents so one agent's failure cannot hang the whole workflow.
  • SHOULD be combined with client-side timeouts and a fallback path.
  • SHOULD give each component or agent an independent breaker per dependency, with thresholds tuned to that dependency's reliability.
  • SHOULD enter a half-open state after a recovery timeout, closing on a successful trial request and reopening on failure.
  • SHOULD return an empty or cached result when open so downstream consumers can degrade gracefully instead of throwing.
  • MUST emit state transitions and alert operators when a circuit stays open beyond the expected recovery window.
  • SHOULD wrap framework-built agents to provide unified resilience across workflows.
  • MUST stop sending requests to a struggling service on elevated error rate or latency and periodically probe for recovery, since continued requests queue additional load.
  • SHOULD be combined with retries with exponential backoff, fallbacks and bulkheads that isolate failure domains.
  • SHOULD open on error-rate or latency thresholds, fail fast, and probe recovery in a half-open state after cooldown.

Quantitative guidance

As stated by the sources; verify before use.

  • Example trip threshold: 50% of requests failing over 60 s; example half-open probe after ~30 s (Ch2.8).
  • Example tuning: external search API 3 failures / 30 s timeout; LLM API 5 failures / 60 s timeout (Ch2.8).
  • Example opens after 5 consecutive failures; > 10 retries per trace signals a potential cascade (Ref8.06).
